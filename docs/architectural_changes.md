# Architectural changes to preserve modularity and generality

## Architectural Principle

Every subsystem should own the concepts that would still exist if every downstream subsystem disappeared.

Examples:

- Experiment owns declarative specifications.
- Transport owns execution, diagnostics, sources, lattices, and loss policies.
- Validation owns references, metrics, convergence, and reporting.
- Visualization consumes transport state but never participates in transport.
- Physics owns numerical algorithms independent of beamline policy.

Dependencies should always point downstream.

## High Priority

### 1. Eliminate `transport/simulation_config.py`

**Motivation**
- `SimulationConfig` is a transitional compatibility adapter.
- The `Experiment` and resolver now form the canonical execution pipeline.
- Runtime objects should not be flattened into a legacy configuration object.

**Target architecture**
- All downstream branches consume resolver output directly.
- Remove intermediate compatibility layers.
- `Experiment` remains the declarative specification.
- The resolver remains the single composition point for runtime objects.

---

### 2. Separate particle existence policy from the transport solver

**Motivation**
- Particle loss is a simulation policy, not a numerical integration concern.
- Current implementation only supports aperture losses, but future transport will include additional termination mechanisms.

**Target architecture**
Create a dedicated loss handling module responsible for evaluating particle survival.

Examples include:
- Aperture losses
- Collimators
- Material interactions
- Absorbers
- Trapping conditions
- User-defined stopping criteria

The transport solver should only evolve particle trajectories and return diagnostics.

---

### 3. Keep the Boris integrator numerically pure

**Motivation**
- This complements #2
- The Boris algorithm should only integrate the relativistic Lorentz equation.
- It should remain independent of beamline-specific physics.

**Responsibilities**
- Advance particle positions and velocities.
- Query electromagnetic fields.
- Perform relativistic time integration.

It should not perform:
- Loss evaluation
- Diagnostics
- Validation
- Reporting
- Visualization

---

### 4. Separate particle sources from the validation framework

**Motivation**
- Particle source is fundamentally a transport concept, not a validation one
- If validation is completely deleted, this class should still exist.

- The resolver calls transport.validation.sources
- Move particle sources into their own package
- Dependency graph:

```
experiment
      │
      ▼
sources      lattice
      │          │
      └────┬─────┘
           ▼
      transport
           ▼
      validation
```

---

### 5. Split validation registry

- This is doing multiple unrelated jobs
- Split into multiple registries, each having one responsibility
- Directly feeds into point #4

---

### 6. Decouple schema.py from validation configuration types

- NumericalConfig comes from validation.config in schema.py
- Same with OutputConfig, PassCriteria, ComparisonDirection
- The experiment schema now imports validation types, ideally schema.py shouldn't know validation exists
- Schema should be completely independent

---


### 8. Move transport execution out of the validation framework

**Motivation**

- Validation should consume transport results, not execute transport.
- The transport layer should own particle propagation and diagnostic generation.
- The current ValidationEngine directly invokes the solver, coupling execution to validation.

- Target architecture

```
Experiment
      │
      ▼
Resolver
      │
      ▼
TransportEngine
      │
      ▼
TransportResult
      │
      ▼
ValidationEngine
```

**Responsibilities:**

- Transport

      - Execute particle transport
      - Generate diagnostics
      - Return transport results

- Validation

      - Resolve references
      - Evaluate metrics
      - Perform convergence analysis
      - Generate reports
      - Determine pass/fail status

---

### 9. Move solver interface and diagnostics into the transport subsystem

**Motivation**

- Solver interfaces are transport abstractions, not validation abstractions.
- Diagnostics are generated by transport and consumed by validation.
- If validation were removed entirely, both concepts would still exist.

- Target architecture

```
transport/
    solver.py
    diagnostics.py
    sources/
    lattice/
    losses/

validation/
    cases/
    references/
    metrics/
    convergence/
    reporting/
```

```
Dependency graph:

transport
      │
      ▼
diagnostics
      │
      ▼
validation
```

- Validation should never own execution-layer abstractions.

---

### 10. Establish a dedicated transport subsystem

***Motivation**

The current dependency graph has execution responsibilities distributed across:

- physics
- validation
- pipeline

There is no subsystem that explicitly owns transport execution.

Target architecture

```
transport/
    engine.py
    solver.py
    diagnostics.py
    losses/
    sources/
    lattice/
    result.py
```

The transport package should become the sole owner of particle propagation, while validation becomes a downstream consumer of transport results.
Points above aim at achieving this achitecture incrementaly.

## Medium Priority


### 1. Remove hardcoded conditionals from build_particle_source()

- Right now the function consists of hard-coded if-elif statements
- Every new source requires editing this function
- Ideally the source registry would own object construction: source_registry.build(spec)
- Each registered source class would know how to instantiate itself from its corresponding ParticleSourceSpec

---

### 2. Make element classes responsible for constructing themselves

- Currently, construction of each lattice element is handled by lattice/registry.py
- Instead of splitting construction into separate functions, everything is handled by the element class itself
- This way, each element owns its physics (field()), visualization (draw()), construction from declarative parameters (from_params())

---

### 3. Introduce a TransportResult object

**Motivation**

Transport currently returns multiple loosely related objects:

- final positions
- final velocities
- alive mask
- diagnostics

As the transport layer grows, more outputs (loss statistics, timing, events, metadata) will naturally appear.

- Target architecture

Instead of

```
R, V, alive, diagnostics = track_particles(...)
```

return

```
TransportResult(
    R=...,
    V=...,
    alive=...,
    diagnostics=...,
)
```

This gives downstream systems (validation, visualization, optimization) a stable interface.

---

### 4. Make Experiment fully declarative

**Motivation**

- The experiment schema currently mixes declarative specifications with runtime configuration objects.

- For example, NumericalConfig and OutputConfig coming directly from the validation package.

- An experiment should describe what to execute, not contain runtime implementations.

Target architecture

Introduce specification types such as

```
NumericalSpec
OutputSpec
ValidationSpec
```

The resolver becomes responsible for translating every specification into runtime objects.

---

### 5. Move parameter normalization into element/source classes

Currently

```
_normalize_params(...)
```

exists inside the registry.

Instead,

```
Dipole.from_params(...)
```

should normalize its own parameters.

That keeps every element responsible for its own declarative interface.

---

## Low priority

### 1. Remove builder callables from ValidationCase

Currently

```
ValidationCase(
    system_builder=...
)
```

contains executable behavior.

Long term, validation should receive an already-built transport result (or lattice), making ValidationCase purely declarative.

---

### 2. Remove special-case logic from the resolver

The resolver currently contains transport-specific logic such as

```
if particle_source == geant4:
    lattice = ...
```

Ideally each subsystem should own its own adaptation.

Examples:

```
Geant4 coordinate adjustment
particle-source-specific initialization
```

should happen inside the source or transport layer rather than in the resolver.

---

### 3. Eliminate compatibility adapters

Just as aimed for SimulationConfig.

Eventually the same should happen for Validator once migration is complete.

Compatibility layers should have a planned removal point.

---

### 4. Standardize registry responsibilities

Right now registries are used inconsistently.

Some construct objects.

Some register strategies.

Some normalize parameters.

Some contain factories.

Registries should map identifiers to implementations. Construction logic belongs to the implementation itself.
